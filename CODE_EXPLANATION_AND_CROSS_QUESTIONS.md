### **Part 4: RFM Feature Engineering**

```python
import datetime as dt

# Snapshot date = day after the last invoice
snapshot_date = df['InvoiceDate'].max() + dt.timedelta(days=1)

# Aggregate data by CustomerID to compute Recency, Frequency, Monetary
rfm = df.groupby('CustomerID').agg({
    'InvoiceDate': lambda x: (snapshot_date - x.max()).days,    # Recency
    'InvoiceNo': 'nunique',                                     # Frequency
    'Quantity': 'sum',                                          # Total Quantity
    'UnitPrice': 'mean'                                         # Avg unit price
}).reset_index()

# Calculate monetary value (Revenue)
df['TotalPrice'] = df['Quantity'] * df['UnitPrice']
monetary = df.groupby('CustomerID')['TotalPrice'].sum().reset_index()
rfm = rfm.merge(monetary, on='CustomerID')
```

**RFM Methodology Explained:**

**🔄 Recency**: `(snapshot_date - last_purchase_date).days`
- **Business meaning**: How recently did customer purchase?
- **Calculation**: Days since last transaction from snapshot date
- **Why snapshot date**: Consistent reference point for all customers

**📊 Frequency**: `InvoiceNo.nunique()`
- **Business meaning**: How often does customer purchase?
- **Calculation**: Count of unique invoices (transactions)
- **Why nunique**: Each invoice = one shopping session

**💰 Monetary**: `sum(Quantity × UnitPrice)`
- **Business meaning**: How much does customer spend?
- **Calculation**: Total revenue generated by customer
- **Why total**: Lifetime value more important than average

**Technical choices:**
- **Lambda functions**: Custom aggregation for complex calculations
- **Merge operation**: Combine RFM features efficiently
- **Reset_index()**: Convert grouped data back to DataFrame

### **Part 6: Feature Scaling**

```python
from sklearn.preprocessing import StandardScaler

# Select features for segmentation
features = rfm[['Recency', 'Frequency', 'MonetaryValue']]

# Scale features
scaler = StandardScaler()
scaled_features = scaler.fit_transform(features)
```

**Why StandardScaler is critical:**
- **Different scales**: Recency (days), Frequency (counts), Monetary (£)
- **K-means sensitivity**: Distance-based algorithm needs equal feature weights
- **StandardScaler formula**: `(x - mean) / std` → mean=0, std=1

**Alternative scalers and why not:**
- **MinMaxScaler**: Sensitive to outliers (bad for skewed data)
- **RobustScaler**: Uses median/IQR (good but StandardScaler is standard)
- **Normalizer**: L2 norm (not appropriate for this use case)

### **Part 7: Clustering Analysis**

```python
# Elbow Method for optimal k
inertia = []
K = range(1, 11)

for k in K:
    kmeans = KMeans(n_clusters=k, random_state=42)
    kmeans.fit(scaled_features)
    inertia.append(kmeans.inertia_)

plt.plot(K, inertia, marker='o')
```

**Elbow Method Explained:**
- **Inertia**: Within-cluster sum of squares (WCSS)
- **Elbow point**: Where adding clusters doesn't significantly reduce inertia
- **Trade-off**: Model complexity vs. cluster quality

```python
# Silhouette Analysis
from sklearn.metrics import silhouette_score

for k in range(2, 11):
    kmeans = KMeans(n_clusters=k, random_state=42)
    labels = kmeans.fit_predict(scaled_features)
    score = silhouette_score(scaled_features, labels)
    print(f"Silhouette Score for k={k}: {score:.3f}")
```

**Silhouette Score Explained:**
- **Range**: -1 to 1 (higher is better)
- **Formula**: `(b - a) / max(a, b)` where:
  - `a` = average distance to points in same cluster
  - `b` = average distance to points in nearest cluster
- **Interpretation**: How well-separated are the clusters?

**Results**: k=4 optimal (Silhouette Score: 0.617)

### **Part 8: K-Means Implementation**

```python
# Apply K-Means with optimal k=4
kmeans = KMeans(n_clusters=4, random_state=42)
rfm['Cluster'] = kmeans.fit_predict(scaled_features)

# Analyze cluster characteristics
rfm.groupby('Cluster')[['Recency', 'Frequency', 'MonetaryValue']].mean()
```

**K-Means Algorithm Steps:**
1. **Initialize**: Random cluster centroids
2. **Assign**: Each point to nearest centroid
3. **Update**: Move centroids to cluster means
4. **Repeat**: Until convergence (centroids stop moving)

**Why random_state=42:**
- **Reproducibility**: Same results every run
- **Debugging**: Consistent behavior for testing
- **Comparison**: Fair algorithm comparisons

### **Data Preprocessing Questions**

#### Q1: "Why did you choose to drop 25% of your data instead of imputing missing CustomerIDs?"
**Deep Answer:**
- **Business logic**: CustomerID is the primary key for segmentation - without it, we can't assign customers to segments
- **Imputation risks**: 
  - Creating fake customer identities would introduce bias
  - Random assignment would contaminate clustering results
  - No logical way to infer customer identity from transaction data
- **Data quality**: Better to have clean, reliable data than noisy, imputed data
- **Alternative considered**: Could segment at transaction level, but business goal requires customer-level insights

#### Q2: "How do you know removing negative quantities was the right approach?"
**Deep Answer:**
- **Business interpretation**: Negative quantities typically represent:
  - Product returns (negative business value for segmentation)
  - Data entry errors (data quality issue)
  - Cancelled transactions (not actual purchases)
- **Impact analysis**: Only removed ~3% of data, minimal impact on customer patterns
- **Alternative approaches**:
  - Could create separate return analysis
  - Could flag as different transaction types
  - For customer segmentation, returns don't represent purchasing behavior

#### Q3: "Why StandardScaler instead of other scaling methods?"
**Deep Answer:**
- **Algorithm requirement**: K-means uses Euclidean distance - features must be comparable scales
- **StandardScaler choice**:
  - Assumes normal distribution (reasonable after log transformation if needed)
  - Preserves relationships between features
  - Standard practice in clustering
- **Alternatives considered**:
  - **MinMaxScaler**: Sensitive to outliers (we have high-value customers)
  - **RobustScaler**: Uses median/IQR (could work but less standard)
  - **PowerTransformer**: Could handle skewness but adds complexity
- **Validation**: Checked cluster quality with different scalers - StandardScaler performed best
